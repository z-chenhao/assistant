# Steward 文档

`docs/` 只维护项目的最新有效说明，不作为开发日志、审查档案或测试运行记录库。更新已有主题时直接修改所属文档；只有独立、长期维护的新主题才新增文件。

## 导航与内容归属

[Feature Map](feature-map.md) 是唯一需求主入口，维护稳定需求 ID、当前状态和所属文档。

| 位置 | 维护内容 |
| --- | --- |
| [功能说明](feature-map.md#需求索引) `features/` | 用户行为、使用方法、安装与运维、当前限制和验收目标 |
| [技术方案](designs/product-overview.md) `designs/` | 当前架构、流程、有效设计理由、兼容约束及明确标注的待实现方案 |
| [测试方案](test-plans/product.md) `test-plans/` | 验收场景、测试入口、证明范围、覆盖缺口和必要的真实环境验证 |
| [界面设计规范](../design.md) | 跨模块导航、设置控件、响应式布局与动效规则 |
| [运行时契约](designs/runtime-contracts.md) | 跨功能的数据、权限、持久化与恢复语义 |

Markdown 页面限于本页、`feature-map.md` 和上述三类目录的直属主题文件；不另设报告或归档层级。三类目录内的 `_template.md` 定义新主题的结构。界面规范入口位于仓库根目录的 [design.md](../design.md)，功能方案链接到该规范，避免重复维护公共 UI 规则。贡献和治理入口位于仓库根目录的 [CONTRIBUTING.md](../CONTRIBUTING.md) 与 [GOVERNANCE.md](../GOVERNANCE.md)，不在 `docs/` 复制维护第二套规则。

## 强制维护规则

1. **原位更新**：行为、架构或流程变化时，同步修改所属功能、设计、测试方案和 Feature Map；正文、图示和命令只呈现当前有效版本，不叠加旧版说明。
2. **按主题组织**：文件名表达稳定主题，不以日期、迭代批次或任务编号建立审查报告、日报、开发日志、执行记录或归档目录。禁止将这类内容移到 `docs/` 的其他位置继续保存。
3. **保留有效理由**：设计文档说明当前采用方案、原因、代价与兼容要求；决定被替代时更新或删除原说明，不维护追加式 Changelog、历史决策表或旧里程碑快照。仍影响使用、升级、恢复和安全的历史格式及迁移约束必须保留在当前说明中。
4. **分清事实与计划**：明确区分已实现行为、已确认待实现方案和待讨论建议。保留真实缺口与未验证项，不通过删掉限制来宣称完成。
5. **过程记录留在开发系统**：变更动机、逐批审查、决策演进和执行结果记录在关联 PR、Issue、Git 历史或 CI 产物中。原始日志和临时验证材料放在忽略的 `evidence/`，不得把一次运行的结果或覆盖率快照变成长期文档。
6. **链接与清理同步**：新增主题必须加入现有导航；删除或合并文档时清理入站链接，保留需求 ID 的去向与仍有效的契约锚点。避免复制相同规则，优先链接所属文档。
7. **合并前检查**：运行 `python3 scripts/check_docs.py`，检查本地链接、导航可达性及日志式文档结构；评审同时核对内容是否准确、是否重复或过时。自动检查不能代替内容审查。

日期可用于真实命令示例、协议字段和仍适用的兼容说明，不得用来组织开发流水账。需求状态与验收的具体维护方式见 [Feature Map 规则](feature-map.md#文档维护规则)。
